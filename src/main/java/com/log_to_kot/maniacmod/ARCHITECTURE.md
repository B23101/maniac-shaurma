# Архітектура maniacmod v4 — модульна реорганізація

> **Перш ніж редагувати будь-який код у цьому проєкті — прочитай
> [`AI_CODE_GUIDE.md`](./AI_CODE_GUIDE.md) у корені репозиторію.**
> Це обов'язкова інструкція (не побажання) для будь-якого розробника
> чи ШІ-асистента: правила пакетної приватності, протокол дій при
> знайденому витоку інкапсуляції, і чек-лист перед додаванням нового
> модуля. Архітектура нижче описує ЩО зроблено; `AI_CODE_GUIDE.md`
> пояснює, як не дати їй розвалитись, коли в неї почнуть дописувати
> логіку.

Це ШАБЛОН-КАРКАС: інтерфейси, абстрактні класи та README у кожній
папці, що показують КОНТРАКТ і РОЗКЛАДКУ. Ігрова логіка (атаки,
ремонт генераторів, ефекти пасток тощо) із поточного мода сюди
НЕ перенесена — це наступний крок, коли каркас затверджено.

## Навіщо це

Зараз (v3) `game/` — це звалище: маньяки, пастки, зони, виживші й
генератори лежать поруч в одному пакеті без спільних контрактів.
Додати нового маньяка чи нову пастку означає копіювати ~200 рядків
і міняти кілька чисел — код дублюється, і одна зміна (наприклад,
як рахується кулдаун) вимагає правок у кожному дублікаті окремо.

v4 будує 6 незалежних модулів. Кожен має:
- **Archetype** (абстрактний клас) — спільні дані й контракт для
  всіх сутностей цього типу (маньяк/пастка/предмет/роль виживого).
- **Registry** (реєстратор) — єдине місце, де перелічені всі
  конкретні різновиди; додати новий тип = додати один запис сюди
  плюс один клас-нащадок Archetype. Жодна інша частина мода не
  змінюється.
- Конкретні підкласи (маньяк, BearTrap, Medkit...) —
  ТІЛЬКИ дані й перевизначені методи, без дублювання спільної
  логіки (вона живе в Archetype).

## Мапа модулів

| Новий пакет         | Що туди йде (з v3)                                             | Конструктор              |
|----------------------|------------------------------------------------------------------|---------------------------|
| `maniacs/`           | `entity/ManiacType.java` (розбити на клас-на-маньяка)             | `ManiacArchetype`         |
| `abilities/`         | нове — здібності маньяків як окремі плагіни                       | `Ability` (інтерфейс)     |
| `traps/`             | `game/BearTrapState.java`, `ElectricWireState.java`, `RopeBindState.java`, `MineState.java` | `TrapArchetype` |
| `survivors/`         | `game/SurvivorData.java` (розділити на роль + стан)               | `SurvivorRole`, `SurvivorState` |
| `items/` (переробка) | `items/ItemImplementations.java` (розбити на клас-на-предмет)     | `ItemArchetype`           |
| `map/zones/`         | `game/GeneratorState.java`, `ExitState.java`, `ItemSpawnZone.java`, `EscapeZone.java`, `ManiacSpawnZone.java` | `ZoneArchetype` |

## Що залишається де є (не чіпається цим кроком)

- `game/ManiacGameManager.java` — центральний координатор матчу
  (лишається як "диригент", але звертатиметься до нових реєстрів
  замість власних switch-ів по enum).
- `network/`, `client/`, `sound/`, `blocks/`, `entity/ManiacEntity.java`,
  `entity/CorpseEntity.java`, `cinematic/`, `mixin/` — інфраструктура,
  не потребує реорганізації за цим запитом.
- `loot/` — окремий модуль, доданий після цього кроку: предмети на
  землі як власна сутність (`entity/GroundItemEntity`), а не ванільний
  `ItemEntity`. `LootModule` розкладає `LootTables` по ITEM-точках
  плану так само, як `map/zones/GeneratorPoi` — генератори; деталі й
  межі — у `loot/README.md`.
- shaurma-lib інтеграція (config/lifecycle/lobby/teleport/overlays) —
  вже виконана окремим кроком раніше, тут не дублюється.

## Принцип "одна зміна → впливає на декілька"

Приклад: зараз якщо треба змінити, як рахується шанс зриву ремонту
генератора для ВСІХ генераторів — це один метод у `GeneratorState`
(вже так, генератор один тип). Але для маньяків: зараз кулдаун атаки
рахується один раз у `ManiacGameManager` за `type.attackCooldownTicks`
напряму по enum — якщо захочеться додати загальний "бонус швидкості
атаки" для ВСІХ маньяків одразу, доведеться шукати місце виклику.
У v4 такий бонус — це один метод в `ManiacArchetype` (базовий клас),
і він одразу діє на всіх маньяків, наявних і майбутніх, бо кожен
успадковує його, а не копіює.

Баланс — окремо від логіки: числа конкретного маньяка лежать у його
власному файлі `config/maniacmod/maniac_stats/<id>.yml`, а код лише
оголошує дефолти для нього (`declaredAttackDamage()` та інші). Це та
сама межа «дані vs логіка», тільки проведена ще раз усередині даних.

Те саме для пасток (спільний кулдаун-модифікатор), предметів
(спільний ефект "зношування") і зон (спільна перевірка "чи гравець
у зоні").

## Наступні кроки (не в цьому кроці)

1. Перенести реальну логіку з v3-класів у v4-підкласи (по одному
   модулю за раз, з тестуванням між кроками).
   2. Переключити `ManiacGameManager` на виклики через нові реєстри
      замість прямих enum switch-ів.
   3. Видалити старі файли з `game/`, `entity/ManiacType.java`,
      `items/ItemImplementations.java` після підтвердження, що нові
      підкласи повністю покривають стару поведінку.

# Доповнення v5 — фази, спавн, головний клас

v4 описав 6 предметних модулів (маньяки, здібності, пастки, виживші,
предмети, зони). v5 додає те, без чого вони не можуть працювати
разом, і розбирає старий головний клас.

## Нові пакети

| Пакет | Що вирішує |
|---|---|
| `core/phase/` | Фази матчу. Єдиний список «технічна / ігрова» + дозволи |
| `core/match/` | Координація матчу і весь його стан в одному об'єкті |
| `spawn/` | Розмітка точок і безконфліктне розкидання по карті 300×300 |
| `loot/` | Предмети на землі: geo-сутності, повороти, таблиці луту |

## Принцип, який тримає все разом

Модулі **не викликають один одного**. Вони підписуються на фази:

```
PhaseManager
   │ onPhaseEnter / onPhaseTick / onPhaseExit
   ├── traps       (тікає, лише коли phase.allows(TRAPS))
   ├── survivors   (стаміна/хп, лише коли allows(SURVIVOR_VITALS))
   ├── generators  (ремонт, лише коли allows(GENERATOR_REPAIR))
   ├── items       (видача на SCATTER, прибирання на RESET)
   └── hud         (мережа/оверлеї, коли allows(HUD))
```

Завдяки цьому нова механіка **додається**, а не **вставляється**:
її не треба вписувати в чужий метод, як було з
`ManiacGameManager.startGame()` і `ServerEventHandler.onServerTick()`.

## Підключення в ManiacMod

```java
// onServerAboutToStart, після ShaurmaLib.init(...)
orchestrator = new MatchOrchestrator();
orchestrator.attachLifecycle(state -> lib.lifecycleModule().lifecycleBus()
    .transitionTo(switch (state) {
        case IDLE   -> MatchLifecycleState.IDLE;
        case ACTIVE -> MatchLifecycleState.ACTIVE;
        case ENDING -> MatchLifecycleState.ENDING;
    }));

orchestrator.registerModule(new TrapModule());
orchestrator.registerModule(new SurvivorModule());
orchestrator.registerModule(new GeneratorModule());
// … далі модуль за модулем
```

`ServerEventHandler.onServerTick()` худне до одного рядка:

```java
orchestrator.tick(event.getServer().getPlayerList().getPlayers());
```

Без `if (getGameState() != RUNNING)` — фільтрація фаз тепер усередині.
