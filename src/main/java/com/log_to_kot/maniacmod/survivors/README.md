# survivors/ — виживші

## Що тут

- **SurvivorRole** — абстрактний базовий клас ролі (хп, слоти
  інвентаря, підсвітка). Зараз один тип (`DefaultSurvivorRole`),
  структура готова до додавання інших ролей.
- **SurvivorState** — ОКРЕМА машина станів (HEALTHY / BROKEN_LEG /
  CRAWLING / UNCONSCIOUS), незалежна від ролі. Один гравець за гру
  проходить кілька станів, лишаючись тією ж роллю.
- **SurvivorRegistry** — список усіх ролей.

## Роль vs Стан — у чому різниця

- **Роль** відповідає на питання "ХТО цей гравець" (постійна
  характеристика на весь матч: скільки в нього максимум хп,
  скільки слотів інвентаря).
- **Стан** відповідає на питання "ЩО з ним ЗАРАЗ" (змінюється
  протягом матчу: зараз здоровий, зараз повзе після поламаної
  ноги, зараз непритомний і чекає на порятунок).

Це навмисно два окремі класи, а не один — так система підняття
непритомного гравця чи лагодження ноги Шиною не залежить від
того, яка роль у постраждалого, і навпаки: додавання нової ролі
не вимагає переписувати логіку станів.

## Падіння, вставання й поламана нога

Життєвий цикл — у `SurvivorModule`, один шлях на кожен крок:

1. **Падіння** (`onFall`). У ігровій фазі для виживого ванільний урон
   від падіння скасовується ЗАВЖДИ — HP рахує `MatchContext`, а не
   ванільне HP гравця. Від порога `fallKnockdownHeightBlocks` гравець
   лягає (`CRAWLING`). Чи зламається нога — залежить від ВИСОТИ
   (`legBreakChanceFor`): нижче `legBreakMinHeightBlocks` нога ціла, далі
   шанс росте лінійно від `legBreakChanceAtMinHeight` до
   `legBreakChanceAtMaxHeight` на `legBreakMaxHeightBlocks` і не росте
   далі. Результат — відкладений злам ноги. Повторне падіння лежачого нічого не скидає.
2. **Лежання** (`beginCrawling` — єдиний вхід у `CRAWLING`, і з падіння,
   і з порятунку непритомного). Рух блокується двома шарами:
   серверний `InteractionLock(MOVEMENT)` (чесність) і клієнтський
   `MixinKeyboardInputDownedMovement` (клавіші й стрибок не доходять до
   симуляції, тож немає «прослизання» між ресинками позиції).
3. **Вставання** (`onStandUpAttempt`). Клієнт шле `StandUpPacket` на
   КОЖНЕ окреме натискання пробілу (фронт, не утримання). Потрібно
   `standUpPresses` натискань (`survivors.yml`, за замовчуванням 10).
   Після кожного сервер шле `StandUpProgressPacket` — на цьому
   тримається шкала вставання. Далі стан стає `BROKEN_LEG` або
   `HEALTHY`.

**Правило стаміни при `BROKEN_LEG`:** стаміна завжди 0, доки Шина не
поверне `HEALTHY`. Три місця, бо одного мало:
`StaminaRules.recoveryEnabled(false)` (`syncLegRules` — бібліотека інакше
відновлює стаміну на END-тіку, ПІСЛЯ нашого модуля), щотікове
притискання до 0 (`tickBrokenLegStamina`) і нуль у пакеті vitals
(`sendVitals` — те, що бачить гравець).

## Хто кого може бити

| Джерело | Результат |
|---|---|
| Удар маньяка (`ManiacCombatModule.onAttack`) | втрата HP → непритомність |
| Падіння (`SurvivorModule.onFall`) | лежання / шанс ноги, БЕЗ втрати HP |
| Виживий → виживий (ЛКМ) | скасовується в `ServerHooks.onAttackEntity` |
| Усе інше ванільне по виживому (снаряд, вогонь, моб, вибух) | блокується інтерцептором `match_damage` у `ManiacMod` |
| Технічні фази (LOBBY, ROLE_REVEAL, …) | не б'є ніхто нікого |

Справжня шкода приходить лише двома власними шляхами (рядки 1–2), які
не викликають ванільний `hurt`, тому інтерцептор їх не блокує.

## v3 → v4

v3 `game/SurvivorData.java` мав спрощену модель (`lives` 1-3 і
прапор `bound`). Презентація "Виживші" описує набагато детальнішу
цільову систему (хп 100, стаміна, поламана нога тощо) — тому
`survivors/` тут ширший за прямий 1:1 перенос: базові класи вже
відповідають цільовій системі, а не поточному v3-коду. Точні числа
(швидкість витрати стаміни, час підняття непритомного) позначені
TODO — уточнити при перенесенні реальної логіки.
