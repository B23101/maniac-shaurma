# core/match — координація матчу

## Файли

- `MatchContext` — увесь стан ОДНОГО матчу. Звичайний об'єкт, не
  статика. Новий матч = новий об'єкт.
- `MatchOrchestrator` — диригент: хто маньяк, коли міняється фаза,
  коли матч закінчено.

## Межа відповідальності

Оркестратор **координує**. Він не тікає пастки, не рахує урон, не
лагодить генератори — це роблять модулі у своїх пакетах.

Правило для перевірки: якщо метод згадує конкретну механіку
(«капкан», «бензин», «стаміна») — він не належить цьому пакету.

## Чому весь стан в об'єкті

v3 тримав стан у `static` полях. Скидання матчу означало двадцять
ручних `.clear()` — і один із них (міни) справді забули. Плюс стан
переживав перезавантаження світу.

Тепер скидання — це `context = new MatchContext()`.

**Пастка цього підходу — те, що НЕ належить матчу.** Розмітка карти
(точки спавну, генераторів, виходів) живе у файлі `points.yml`, а не в
матчі. Новий порожній `MatchContext` не знає про неї, тому після
`context = new MatchContext()` розмітку треба явно повернути —
`reset()` робить це викликом `reloadConfiguredMap()` вже ПІСЛЯ входу в
`LOBBY` (поза лобі цей метод нічого не чіпає). Без цього другий матч
бачив би нуль точок, хоч файл повний.

Так само для всього, що додасться в майбутньому: якщо дані не мають
зникати разом із матчем — вони не в `MatchContext`, а значить, їх
треба підвантажувати після скидання.
