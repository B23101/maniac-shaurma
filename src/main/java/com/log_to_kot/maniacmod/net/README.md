# net — мережевий шар

## Форма

- `ModPacket` — спільний контракт: `encode(buf)` + `handle(ctx)`
- `S2CPacket` — розширює `ModPacket` для напрямку сервер→клієнт;
  `handle()` тут `final` і сам робить `DistExecutor`-обгортку —
  конкретний пакет реалізує лише `clientHandle()`
- `ModNetwork` — канал, реєстрація, відправка
- `s2c/` — сервер → клієнт, розкладено за категоріями (нижче)
- `c2s/` — клієнт → сервер, розкладено за категоріями (нижче)

Пакети — `record`. Декодер — це конструктор `Xxx(FriendlyByteBuf)`,
тому кодування й декодування видно поруч, в одному файлі.

## Категорії `s2c/` — за ЗМІСТОМ даних, не за місцем виводу

Пакет називається й кладеться за тим, ЩО він несе, а не ЗА ЯКИМ
UI-компонентом його показують ("tab", "hud", "scoreboard" — не
категорії). Причина: один компонент UI завтра може підписатись на
кілька категорій, а одна категорія — живити кілька компонентів.
Якщо пакет називати за місцем виводу, рано чи пізно туди почне
падати випадкова інформація "бо це вже й так летить у той самий
UI" — так з'являється дублювання одних і тих самих даних у двох
пакетах з різними назвами.

| Пакет | Що це | Частота | Приклади |
|---|---|---|---|
| `identity/` | хто я (роль/архетип) | раз на матч | `RoleSyncPacket` |
| `matchstate/` | стан, спільний для всіх гравців | на подію матчу | `PhaseSyncPacket`, `RosterSyncPacket` |
| `vitals/` | показники ВЛАСНОГО гравця | часто (по зміні) | `SurvivorVitalsPacket` |
| `actionprogress/` | прогрес дії, що триває зараз | по дії | `GeneratorProgressPacket`, `GeneratorHighlightPacket`, `AbilityCooldownPacket` |
| `notify/` | одноразова подія, не стан | на подію | `ActionBarPacket`, `CountdownPacket` |

`RosterSyncPacket` (зведення по ВСІХ гравцях, таб-екран) лежить у
`matchstate/`, а не в окремій `roster/`: це проєкція вже наявного
стану матчу без власної логіки обчислення — той самий випадок, який
колишній план у `s2c/roster/README.md` прямо передбачав.

Виняток: `RosterEntry` таки несе `hp`/`maxHp` — свідомо, не як
випадковий дубль. `vitals` лишається джерелом правди для ВЛАСНОГО
HUD гравця; `RosterEntry.hp` — для чужого хп у таб-таблиці (інший
глядач, інша причина існування числа). Повне обґрунтування — у
docstring `RosterSyncPacket`. stamina/heartbeat туди свідомо НЕ
додані: таб їх не показує.

**Перед тим як додати нове поле в наявний пакет** — спитай: це той
самий сенс, що вже є в іншій категорії, просто для іншого глядача чи
іншого UI? Якщо так — не дублюй число, а або перевикористай наявний
пакет (`vitals` для власника завжди `vitals`, хто б не дивився), або
додай посилання (`UUID` + вже наявний enum/тип), а не копію значення.
Саме так стався дубль у v3: два пакети возили одні й ті самі дані під
різними іменами, бо кожен був "прив'язаний" до свого UI-екрана.

## Категорії `c2s/` — за формою наміру

| Пакет | Форма | Приклади |
|---|---|---|
| `intent/` | одноразове натискання, без стану | `AbilityActivatePacket`, `TrapPlacePacket`, `HighlightTogglePacket`, `StandUpPacket` |
| `hold/` | утримання: явний початок/кінець | `RescueHoldPacket` |
| `selection/` | вибір одного варіанту з переліку в UI | `ManiacSelectPacket` |

## Додати пакет

1. Визнач категорію ПЕРШОЮ (за таблицею вище), потім клас у
   відповідній підпапці `s2c/<категорія>/` або `c2s/<категорія>/`.
   S2C-пакет реалізує `S2CPacket` і `clientHandle()`; C2S — `ModPacket`
   і повний `handle(ctx)` напряму (виконується вже на сервері).
2. Один рядок у `ModNetwork.register()` — **у кінець свого блоку**.
3. Якщо змінено формат наявного пакета — підняти `PROTOCOL_VERSION`.
4. Якщо жодна категорія не підходить — це сигнал додати нову
   категорію (підпапку) в таблицю вище, а не запихати пакет
   у найближчу за формою, але не за змістом.

⚠ ID пакета = його позиція в списку `ModNetwork.register()`, а не
розташування файлу в підпапках — переміщення файлу між категоріями
саме собою нічого не ламає, лише порядок у `register()` критичний.
Вставка нового пакета всередину списку зсуває решту: клієнт старої
версії читає чужі байти.

## Правила

**Клієнт надсилає намір, не результат.** `AbilityActivatePacket` каже
«натиснуто E», а не «здібність спрацювала». Сервер перевіряє все сам —
роль, фазу, кулдаун. Клієнтські перевірки в `ClientInputHandler` є, але
тільки щоб не слати свідомо марні пакети.

**Пакет не торкається клієнтських класів напряму, крім як через
`S2CPacket.clientHandle()`.** Базовий контракт сам ховає
`DistExecutor`-виклик — конкретний record ніколи не пише
`DistExecutor` чи `Dist.CLIENT` власноруч, лише викликає потрібний
метод `ClientPacketHandler` усередині `clientHandle()`. Інакше
виділений сервер падає з `NoClassDefFoundError`, бо `@OnlyIn(CLIENT)`
класи з нього вирізані.

**Текст передається ключем локалізації, не готовим рядком.** Інакше
мова повідомлень прив'язана до сервера, а не до гравця.

**Нічого не слати щотік.** `AbilityCooldownPacket` надсилається один
раз із повною тривалістю, клієнт відлічує сам. У v3 цей пакет летів
20 разів на секунду. Так само підсвітка генераторів: один пакет,
клієнт гасить її сам через `durationTicks`.

**Одна порція даних — один пакет, одна категорія.** Перш ніж
створювати новий s2c-пакет, перевір таблицю категорій: якщо дані вже
летять в іншому пакеті (навіть під іншою назвою чи для іншого
глядача) — не дублюй, перевикористай або додай посилання. Це правило
існує саме через попередній досвід дублювання (детальніше в
`roster/README.md`).

## Канали

Мод має власний канал (`maniacmod:main`), окремо від
`shaurma_lib:main`. Версії пакетів мода й бібліотеки не перетинаються.
